Independent verification of TactiQ OS releases

Two scripts, written from the published artefacts and the specifications — not by running the vendor's own tooling.

⬇ verify-tactiq-release.py Release artefacts: the signed sums, the signature and its certificate, the Rekor inclusion proof, and the boot PCR reference recomputed from the images themselves. Python 3, standard library and openssl. No network.
⬇ verify-tactiq-l3.py The attestation evidence: certificate chains, the registration record, and the TPM quotes — parsed and verified from the TPM specification in Python, because tpm2-tools was not available. No network.
python3 verify-tactiq-release.py /path/to/release-dir
python3 verify-tactiq-l3.py /path/to/rc13-dir

TactiQ OS publishes, in advance, the values a correctly built and correctly booted unit should present. That design invites a stranger to check it. These are the checks one stranger wrote, and what they established.

The operating system is public and MIT licensed at github.com/revenue7-eng/tactiq-os. Nothing here is affiliated with that project.

What they reported

Re-run backwards, 29 September, with the hardened checker

A verifier that gets stronger should be re-pointed at everything it previously passed. After the corrections and the attacks described below, both scripts were run again from the oldest release forward:

rc11 — 10 passed, 0 failed. rc12 — 12 passed, 0 failed. rc13 — 12 passed, 0 failed on artefacts and 24 passed, 0 failed on the L3 evidence. The same numbers reported at the time, produced by a stricter script. Nothing previously passed was retroactively invalidated.

rc11 and rc12 ship no L3 attestation evidence, and the L3 checker refuses them — exit 2, nothing verified — rather than reporting a pass over absent evidence.

v2.1.0-rc11  — 10 checks passed, 0 failed
v2.1.0-rc12  — 12 checks passed, 0 failed
v2.1.0-rc13  — 12 checks passed, 0 failed  (release artefacts)
v2.1.0-rc13  — 24 checks passed, 0 failed  (L3 attestation evidence)

The release checker was written against rc11 and run unmodified against rc12 and rc13. A verifier adjusted until it passes is not a verifier.

Changed on 29 September, after this page was linked

Readers arriving from elsewhere should know the page has moved since. The pinned Infineon root is now corroborated against the copy Infineon itself publishes — byte-identical — so that limit is closed. A sixth suggestion was added because of the release root.

This block previously said the release root "rests on one channel". That was our own overstatement, and it is corrected here. The root is not itself listed in the signed SHA256SUMS — but the reference manifest that carries its key hash is, so a root substituted on the release page after the tag was signed does not survive the run. Measured rather than argued: substituting a self-signed root under the same filename fails three checks and exits 1. What remains is narrower and real — control of the repository from the start, which nothing inside the repository can answer. The full account is below.

Since then the vendor has published the root fingerprint outside the release archive, on the public catalog. Checked here rather than taken on trust: the value he publishes is byte-identical to the one computed independently from the release asset. He notes himself that the catalog sits on the same account, so it corroborates the value without yet being an independent channel.

Two observations were raised against rc11: the release set carried no transparency-log evidence, so a signature checked after its ten-minute certificate expired said nothing about when it had been made; and only the leaf certificate was present. Both were closed in rc12, which carries a Sigstore bundle with the certificate, the Rekor inclusion proof and its timestamp. The proof recomputes offline, and the entry was logged one second after the certificate became valid — so the signature is shown to have been made while it was live, by the log rather than by assumption.

For rc13, both TPM quotes are genuine attestation structures, both signatures verify under the registered key, both bind to their own message through extraData, and both attested boot states match the reference recomputed independently from the signed manifest.

The vendor broke this script, and was right to

29 September. Handed the L3 checker, TactiQ did the thing worth doing with someone else's verifier: they tried to make it pass something it should not.

It trusted signing-ca.pem and infineon-root.crt from inside the evidence archive, using openssl's -partial_chain — which means "treat this supplied CA as a trust anchor". The archive's own SHA256SUMS is unsigned. So they altered a field in the registration record, re-signed it under a CA of their own, replaced the three files and recomputed the sums. The script reported 15 passed, 0 failed on a forged set. Reproduced here before fixing it, and the old script does indeed pass the forgery.

A verifier that takes its trust anchors from the thing it is verifying is not a verifier. Three changes, all theirs:

  • the registration record is now anchored at release-root-r2.pem, a published release asset from outside the archive, with signing-ca.pem passed as an untrusted intermediate rather than a trust anchor;
  • the Infineon root is pinned by SHA-256 fingerprint in the script, and the archive's copy is compared against it before being used for anything;
  • the Registration Signer's extended key usage is checked, since -purpose any does not look at it at all.
genuine rc13  — 24 checks passed, 0 failed  (was 15)
the forged set  — REJECTED: the record does not chain to the release root
swapped Infineon root — REJECTED by the pin
substituted EK certificate — REJECTED: does not match the signed record
signer swapped for another valid leaf — REJECTED: not the Registration Signer
any required file deleted — REJECTED: absent evidence is not a passed check
no external release root — REJECTED: nothing to anchor to

A second finding, ours rather than theirs, and worse. Attacking the fixed script from the other direction showed it could be beaten with no cryptography at all: delete the evidence you cannot forge. Removing ak.pub left both quote signatures unverified and still reported zero failures; removing the registration signature skipped that check entirely. The script noted each absence and carried on. Required evidence is now required — a missing file is a failure, not a note — and every deletion above is rejected.

Two smaller gaps closed with it: the EK certificate and the manufacturer intermediate are now compared against the copies named in the signed record, since the archive's own checksums are unsigned and could otherwise carry a substitute; and the attested boot state is matched against both boot slots in the reference, because hardcoding slot A would have reported a genuine slot-B boot as drift.

The script also refuses to use a release root found inside the archive at all: an anchor that travels with the thing it anchors is not an anchor.

That pin was first observed in the rc13 set, which on its own would detect a changed root and not one forged before anyone looked. On 29 September it was compared against the copy Infineon itself publishes, at pki.infineon.com/OptigaRsaRootCA/OptigaRsaRootCA.crt — 1455 bytes DER, TLS chain verified, CN = Infineon OPTIGA(TM) RSA Root CA, serial 03, valid 2013 to 2043. Byte-identical to the copy in the evidence archive. The pin no longer rests on the vendor's own bundle.

What that does not establish: that Infineon's own endpoint is uncompromised, and that the comparison was made in 2026 rather than in 2013. Independent, not absolute. The script itself stays offline — the fingerprint is hard-coded and nothing is fetched at run time.

Two fields in the registration record

Both read false and neither is a fault. Recorded here because a reviewer meeting them cold would reasonably misread the first, and the vendor asked that this page say so until the record itself is changed.

signed: false — a naming artefact, not a missing signature

Per the vendor: the registrar writes the record unsigned, and the Registration Signer leaf signs the file afterwards as a detached signature, so the field stays false because a signature is never a field. Read literally it says the opposite of what a reviewer holding the .p7s sees. The detached signature exists and verifies — it is check three in verify-tactiq-l3.py. The field is to be renamed or dropped in a future record.

revocation_checked: false — accurate as written

It means what it says: nobody fetched the CRL. The EK chain still verifies to the pinned Infineon root, which is the part that matters. The vendor has said capturing the CRL at registration time, with its own timestamp, goes into the next registration.

A crash is not a verdict — exit codes, and a correction to something said elsewhere

Fed malformed or truncated evidence, this checker used to raise, print a traceback and exit 1 — the same code as "a check failed". So a reader could not tell a broken run from a result, and every check after the exception never ran. Found on 29 September by feeding the published script garbage, and fixed.

0all checks passed
1checks ran and at least one failed
2refused to start — no evidence present, or bad arguments. Nothing was verified
3the checker itself broke — the run was abandoned part way. Not a pass, not a failed check

A note for anyone arriving from a message of mine that mentioned a crash: three other defects found that day were in unrelated code of ours, not in either script on this page. The one that belongs here is the one above, and it is fixed. Both scripts now refuse rather than crash, and say which of the four things happened.

Where the checks stop

Credential activation cannot be replayed by a third party

It requires the TPM's private endorsement key. The link between the attestation key and the physical TPM therefore rests on the registrar's signed statement. These scripts verify that the statement is properly signed. They do not, and cannot, verify that it is true. The vendor states this limit himself.

A signature binding is not a reproducible build

The certificate binds the signature to a commit, workflow and tag. It does not establish that the published binaries follow from that source. In the vendor's own words, the commit tells you which code signed the list, not which code produced the files.

The release root — corrected 29 September, and now a check

This page previously said the release root was bound by nothing and that a run trusted the release page alone. That was too broad, and the vendor corrected it. The root is not listed in SHA256SUMS directly — but the signed reference manifest carries its public-key hash at keys.release_root.spki_sha256, and the manifest itself is covered by the Sigstore-signed sums.

Verified here rather than taken on his word: the root's SPKI SHA-256 is 8ecf5465b921e80e…, that exact value appears in rim-rock5a.json, and the manifest's own digest (50bb82770fbf8655…) matches the entry in the signed sums. So a root swapped on the release page after the tag was signed is caught — and the checker now catches it, rather than printing a caveat about it. A swapped root fails the run.

A hole this correction opened, found by attacking it. The first version of the check was circular: the manifest names the root, and the manifest's own signature chains to that root, so an attacker who forged a root and re-signed the manifest satisfied both. Demonstrated here before it was fixed. The property the vendor described is a Sigstore one, and the checker now requires it: the manifest's bytes must match the entry in the release SHA256SUMS — the file the workflow signs with a Rekor inclusion proof — before anything it names is used. Forged root plus re-signed manifest now fails.

What still stands, narrower. The workflow and the release page are one channel, so this establishes nothing against whoever controls the repository from the start. For that, the fingerprint has to be confirmed somewhere the publisher does not control. The vendor states he is putting it in the article and on the catalog, and notes the catalog shares the same account — so that half is his to close, and he says so himself.

He also reports a second binding, in the coverage file. That one is not verified here: the file is not in the evidence archive we hold, so this page records it as his statement and not as a check.

The transparency-log checkpoint signature is not verified

That needs the log's public key. The scripts recompute the root implied by the inclusion proof and compare it to the root the bundle states. Agreement proves the entry is consistent with that root; it does not prove the root is the live log's. Each script says so in its own output.

What would let a stranger check more

Six observations from actually running the checks. None is a fault, and two the vendor has already stated himself — recorded because an outsider arriving at the same place independently is worth more than the suggestion. All five were put to the vendor directly as well. Nothing on this page reaches him from this page.

1. Sign the evidence archive's SHA256SUMS

This one is the root of both problems found this week, and it is the only suggestion here that would have prevented either. The archive's checksum list binds its files to each other and to nothing outside itself. That is what let a re-signed set pass the checker — carrying its own trust anchor — and what let deleted evidence pass it, because nothing stated which files should have been present. Every fix since has been a way of reaching around that gap: anchoring the record outside the archive, pinning the manufacturer root in the script, enumerating the required files by hand. One detached signature over the archive's own sums, under the release hierarchy already in use, would collapse all of it into a single check a reader cannot forget to make — and a signed manifest names what should be there, which closes the deletion route outright.

Measured on rc13. Of the release files this verification touches, three sit outside the Sigstore-signed SHA256SUMS: the evidence archive, the verification instructions that tell a reviewer what to check, and the release root. The reference manifest and its CMS signature are inside — which is precisely why the root-substitution check above holds. The vendor has accepted this suggestion and reports that all three will be carried in the signed sums at the next release; he raised the archive gap himself before it was put to him, and agreed the release root should join them — noting accurately that this adds completeness rather than independence, since the manifest already binds the root's key under the same signature.

2. Publish the release root's fingerprint on a second surface — done

The verification procedure already tells a reviewer to confirm the release root through a channel independent of the release page. When this was written there was nowhere to do that: the root arrived with the release, and it is not inside the signed SHA256SUMS. Printing the fingerprint on a different host would turn a correct instruction into one a stranger can actually follow. It is the other half of suggestion 1: signing the sums anchors the archive, publishing the root anchors the anchor.

The vendor has done this. The fingerprint now appears on the public catalog page, and the value published there is byte-identical to the one computed here from the release asset — checked, not assumed. He notes the catalog shares the release account, so a reviewer gains corroboration rather than independence; he states he has also put it in the accompanying article.

3. Ship the transparency log's public key with the release — on the vendor's list

The smallest change of the five. The inclusion proof recomputes offline and agrees with the root the bundle states, but the checkpoint signature cannot be verified without the log's key — so the entry is provably consistent with that root, and the root is not provably the live log's. One file closes it; everything else needed is already in the bundle.

4. revocation_checked is false

The EK chain verifies to the pinned root, which is the hard part. Fetching the CRL at registration time and recording the result with the CRL's own timestamp would carry that evidence forward, so a check a year later gets it without a live lookup. Accepted by the vendor — it goes into the next registration. See the note above.

5. Build the images inside the workflow — acknowledged as the largest rung still open

The vendor's own point: images are built on their machine and only the sums file is signed by CI, so the commit binds the signature rather than the build. Building in the workflow would extend provenance from the list to the artefacts. The largest rung still open.

6. A machine-readable verdict per release — on the vendor's list

The expected values live in prose today — the PCR selection, the digest, the power-cycle condition. A small verify.json carrying those and the list of checks would let any CI consume them, and would let the power-cycle condition be enforced by a verifier rather than remembered by a reader. A condition that lives only in prose cannot be enforced.

Why bother

A published reference turns checking from a request for assurance into arithmetic. The party being checked publishes what a correct instance should present; anyone can compare, later, offline, without asking. What makes that worth anything is that somebody actually does it — and says where it stops.
